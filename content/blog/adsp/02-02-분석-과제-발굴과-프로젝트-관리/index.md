## 요약

- 분석 과제는 문제가 주어진 상태에서 답을 찾는 **하향식 접근**과, 데이터에서 문제를 찾아내는 **상향식 접근**으로 발굴한다.
- 하향식 접근은 문제 탐색, 문제 정의, 해결 방안 탐색, 타당성 검토의 4단계다.
- 상향식 접근은 디자인 사고의 발산 단계에 해당하고, 비지도 학습과 프로토타이핑을 쓴다.
- 실제로는 상향식으로 넓게 아이디어를 낸 뒤(발산) 하향식으로 좁히는(수렴) 과정을 반복한다.
- 분석 프로젝트는 데이터 크기, 데이터 복잡성, 속도, 분석 복잡성, 정확도와 정밀도의 다섯 가지 특성을 관리하고, KS A ISO 21500의 10가지 영역으로 관리한다.

## 1. 분석 과제 발굴: 하향식 접근

**하향식 접근(Top Down Approach)** 은 문제가 주어지고, 그 해법을 찾기 위해 단계적으로 진행하는 방식이다.

### ① 문제 탐색(Problem Discovery)

문제를 빠짐없이 찾기 위해 틀을 쓴다. 대표적인 틀이 **비즈니스 모델 캔버스**를 단순화한 다섯 영역이다.

| 영역 | 살펴볼 질문 |
|---|---|
| 업무(Operation) | 제품과 서비스를 만드는 내부 프로세스에 개선할 점이 있는가 |
| 제품(Product) | 제품과 서비스를 개선할 점이 있는가 |
| 고객(Customer) | 고객과 채널에 관련된 문제가 있는가 |
| 규제와 감사(Regulation & Audit) | 품질, 규제, 감사에 관련된 문제가 있는가 |
| 지원 인프라(IT & Human Resource) | 시스템과 인력에 관련된 문제가 있는가 |

시야를 회사 바깥까지 넓히는 관점도 있다. 이를 **분석 기회 발굴의 범위 확장**이라고 한다.

| 관점 | 살펴볼 대상 |
|---|---|
| 거시적 관점 | STEEP: 사회(Social), 기술(Technological), 경제(Economic), 환경(Environmental), 정치(Political) |
| 경쟁자 확대 관점 | 대체재, 경쟁자, 신규 진입자 |
| 시장의 니즈 변화 관점 | 고객, 채널, 영향자(influencer) |
| 역량의 재해석 관점 | 내부 역량, 파트너 네트워크 |

이 밖에 같은 업종이나 비슷한 업종의 분석 사례를 벤치마킹하는 **외부 참조 모델 기반 문제 탐색**도 쓴다. 찾은 문제는 **분석 유즈케이스**로 정리해 두면 다음 단계로 넘기기 쉽다.

### ② 문제 정의(Problem Definition)

비즈니스 문제를 데이터로 풀 수 있는 **데이터 문제**로 바꾸는 단계다.

| 비즈니스 문제 | 데이터 분석 문제 |
|---|---|
| 고객 이탈이 늘고 있다 | 이탈에 영향을 주는 요인을 찾고, 이탈 가능성을 예측한다 |
| 재고 비용이 높다 | 상품별 수요를 예측해 적정 재고량을 정한다 |

### ③ 해결 방안 탐색(Solution Search)

분석 기법과 시스템, 분석 역량을 이미 가졌는지에 따라 해결 방안이 달라진다.

| | 분석 역량 확보 | 분석 역량 미확보 |
|---|---|---|
| 기존 시스템 활용 | 기존 시스템 개선 활용 | 교육 및 채용을 통한 역량 확보 |
| 신규 도입 | 시스템 고도화 | 전문 업체 소싱(Sourcing) |

### ④ 타당성 검토(Feasibility Study)

| 타당성 | 내용 |
|---|---|
| 경제적 타당성 | 비용 대비 편익을 따진다. 비용은 데이터, 시스템, 인력, 유지보수 비용이고, 편익은 분석으로 얻는 실질적 가치다 |
| 데이터 및 기술적 타당성 | 필요한 데이터가 있는지, 분석 시스템 환경과 분석 역량이 충분한지 따진다 |

## 2. 분석 과제 발굴: 상향식 접근

**상향식 접근(Bottom Up Approach)** 은 문제를 정의하기 어려울 때, 데이터를 먼저 보고 문제를 찾아 가는 방식이다. '왜(Why)'를 따지기보다 '무엇(What)'이 데이터에 있는지 있는 그대로 관찰한다.

상향식 접근이 필요한 이유는 다음과 같다.

- 문제가 무엇인지조차 분명하지 않을 때가 많다.
- 필요한 데이터가 있는지 불확실하다.
- 데이터를 어떤 목적으로 쓸지가 계속 바뀐다.

### 디자인 사고

스탠퍼드 대학교 디자인 스쿨(d.school)은 **디자인 사고(Design Thinking)** 에서 공감(Empathize)을 출발점으로 강조한다. 디자인 사고는 가능한 아이디어를 넓게 펼치는 **발산(Diverge)** 과, 그중 좋은 것을 좁혀 가는 **수렴(Converge)** 을 반복한다. 상향식 접근이 발산을, 하향식 접근이 수렴을 맡는다.

### 비지도 학습과 지도 학습

| 구분 | 특징 | 기법 예 |
|---|---|---|
| 비지도 학습(Unsupervised Learning) | 정답(목표 변수) 없이 데이터 자체의 패턴을 찾는다. 상향식 접근에서 주로 쓴다 | 장바구니 분석(연관분석), 군집분석, 기술통계, 프로파일링 |
| 지도 학습(Supervised Learning) | 정답이 있는 데이터로 학습해 새 데이터의 정답을 예측한다 | 분류, 추측, 예측, 최적화 |

### 프로토타이핑 접근법

**프로토타이핑 접근법**은 완벽한 계획 대신 일단 분석을 해 보고, 결과를 보며 계속 개선하는 시행착오 방식이다. 진행 순서는 다음과 같다.

1. 가설을 세운다(hypotheses).
2. 디자인을 실험한다(design experiments).
3. 실제 환경에서 테스트한다(test).
4. 테스트 결과에서 통찰을 얻고 가설을 확인한다(insight).

> **쉬운 설명**
>
> 하향식은 '이번 주 저녁 메뉴가 고민이다 → 원인은 장보기 계획이 없어서다 → 식단표를 짜자 → 예산 안에서 되는지 보자'처럼 문제에서 출발한다. 상향식은 냉장고 문을 열어 보고 '달걀과 토마토가 많네, 토마토 달걀볶음을 해 볼까?'처럼 가진 재료(데이터)에서 출발한다. 일단 한 접시 만들어 맛을 보는 게 프로토타이핑이다.

### 분석 과제 정의서

발굴한 과제는 **분석 과제 정의서**로 정리한다. 분석명, 분석 정의, 필요 데이터와 데이터 소스, 분석 방법, 데이터 입수 및 분석 난이도, 분석 수행 주기, 상세 분석 과정, 분석 결과 검증 책임자(오너십) 등을 적는다. 이 문서가 다음 단계인 프로젝트 수행 계획의 입력이 된다.

## 3. 분석 프로젝트 관리 방안

### 분석 과제의 다섯 가지 주요 특성

| 특성 | 관리 포인트 |
|---|---|
| 데이터 크기(Data Size) | 분석할 데이터의 양을 고려한다 |
| 데이터 복잡성(Data Complexity) | 정형, 비정형 데이터가 여러 시스템에 흩어져 있으면 통합과 전처리가 어렵다 |
| 속도(Speed) | 결과가 언제 필요한지에 따라 일 단위 배치인지 실시간인지 정한다 |
| 분석 복잡성(Analytic Complexity) | 복잡한 모델은 정확하지만 해석이 어렵다. 해석력과 정확도 사이의 균형을 잡는다 |
| 정확도와 정밀도(Accuracy & Precision) | 정확도는 모델 값과 실제 값의 차이가 작은 정도, 정밀도는 모델을 반복해 썼을 때 결과가 흩어지지 않는 정도다 |

정확도(Accuracy)와 정밀도(Precision)는 서로 맞바꾸는(trade-off) 관계인 경우가 많다. 결과를 실제 업무에 쓰는 측면에서는 정확도가, 결과가 안정적으로 나오는지 보는 측면에서는 정밀도가 중요하다.

> **쉬운 설명**
>
> 다트를 던진다고 생각하면 쉽다. 화살이 과녁 한가운데 근처에 꽂히면 정확도가 높고, 어디에 꽂히든 화살끼리 촘촘히 모여 있으면 정밀도가 높다. 한가운데에서 멀어도 한곳에 모여 있으면 정밀하지만 정확하지는 않다.

### 분석 프로젝트의 특성

분석가는 데이터 영역과 비즈니스 영역을 함께 이해하고, 둘 사이를 잇는 **조정자** 역할을 해야 한다. 분석 프로젝트는 처음 의도한 결과가 바로 나오지 않는 경우가 많아서, 결과를 보며 반복 개선하는 프로토타이핑 방식의 **애자일(Agile) 프로젝트 관리**도 고려해야 한다.

### 분석 프로젝트 관리 영역(KS A ISO 21500)

| 영역 | 분석 프로젝트에서 특히 신경 쓸 점 |
|---|---|
| 통합(Integration) | 프로젝트 관리 프로세스가 서로 어긋나지 않게 통합한다 |
| 이해관계자(Stakeholder) | 데이터 전문가, 비즈니스 전문가, 분석 전문가, 시스템 전문가가 함께하므로 이해관계자를 식별하고 관리한다 |
| 범위(Scope) | 데이터의 형태와 양, 적용 모델에 따라 범위가 자주 바뀐다. 최종 결과물이 보고서인지 시스템인지에 따라서도 범위가 크게 달라진다 |
| 자원(Resource) | 고급 분석 인력과 빅데이터 아키텍처 전문가를 확보한다 |
| 시간(Time) | 처음 의도한 결과가 쉽게 나오지 않으므로, 정해진 기간 안에 끝내도록 타임 박싱(Time Boxing) 으로 일정을 관리한다 |
| 원가(Cost) | 외부 데이터 구매, 상용 분석 도구 도입 비용을 미리 따진다 |
| 리스크(Risk) | 데이터를 확보하지 못하거나 분석 결과가 기대에 못 미칠 위험을 식별하고 대응 방법(회피, 전이, 완화, 수용)을 정한다 |
| 품질(Quality) | 품질 통제(Quality Control)와 품질 보증(Quality Assurance)으로 나눠 관리한다 |
| 조달(Procurement) | 외부 소싱과 오픈소스 도구 활용을 검토한다. 개념 검증(PoC, Proof of Concept)에는 오픈소스가 유용하다 |
| 의사소통(Communication) | 전문가가 아닌 사람도 결과를 이해할 수 있게 공유한다 |

## 헷갈렸던 것들

- 하향식 접근 4단계 순서는 문제 탐색 → 문제 정의 → 해결 방안 탐색 → 타당성 검토다.
- STEEP의 E는 두 개다. 경제(Economic)와 환경(Environmental)이다.
- 상향식 접근은 '왜'가 아니라 '무엇'에 초점을 둔다. 주로 **비지도 학습**을 쓴다.
- 디자인 사고에서 상향식은 발산, 하향식은 수렴에 해당한다.
- 분석 역량은 없고 시스템도 새로 도입해야 하면 **전문 업체 소싱**이다.
- 분석 프로젝트의 시간 관리 기법은 **타임 박싱**이다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 하향식 접근 | 문제를 먼저 정의하고 해법을 찾는 방식 |
| 상향식 접근 | 데이터를 먼저 관찰해 문제를 찾는 방식 |
| 비즈니스 모델 캔버스 | 업무, 제품, 고객, 규제와 감사, 지원 인프라로 문제를 탐색하는 틀 |
| STEEP | 사회, 기술, 경제, 환경, 정치의 거시적 관점 |
| 디자인 사고 | 공감에서 출발해 발산과 수렴을 반복하는 문제 해결 방식 |
| 타임 박싱 | 작업마다 정해진 시간 안에 끝내도록 일정을 관리하는 기법 |

## 복습 문제

**1.** 하향식 접근법의 단계 순서로 옳은 것은?

① 문제 탐색 → 문제 정의 → 해결 방안 탐색 → 타당성 검토 ② 문제 정의 → 문제 탐색 → 해결 방안 탐색 → 타당성 검토 ③ 문제 탐색 → 해결 방안 탐색 → 문제 정의 → 타당성 검토 ④ 타당성 검토 → 문제 탐색 → 문제 정의 → 해결 방안 탐색

**2.** 분석 기회 발굴의 범위를 넓히는 거시적 관점 STEEP에 포함되지 않는 것은?

① 교육 ② 사회 ③ 기술 ④ 정치

**3.** 상향식 접근에 대한 설명으로 옳지 않은 것은?

① 문제 정의가 어려울 때 쓴다 ② 비지도 학습 기법을 주로 쓴다 ③ 디자인 사고의 수렴 단계에 해당한다 ④ 프로토타이핑으로 시행착오를 거치며 해결한다

**4.** 분석 역량이 없고 분석 시스템도 새로 도입해야 할 때 알맞은 해결 방안은?

① 기존 시스템 개선 활용 ② 시스템 고도화 ③ 전문 업체 소싱 ④ 교육 및 채용을 통한 역량 확보

**5.** 모델을 반복해서 썼을 때 결과가 흩어지지 않고 일정하게 나오는 정도를 뜻하는 것은?

① 정밀도(Precision) ② 정확도(Accuracy) ③ 데이터 복잡성 ④ 분석 복잡성

## 답과 풀이

1. ① 문제 탐색 → 문제 정의 → 해결 방안 탐색 → 타당성 검토 순서다.
2. ① STEEP은 사회, 기술, 경제, 환경, 정치다.
3. ③ 상향식 접근은 발산 단계에 해당한다. 수렴은 하향식 접근이다.
4. ③ 역량도 시스템도 없으면 외부 전문 업체에 맡긴다.
5. ① 반복했을 때 편차가 작은 정도는 정밀도다.
