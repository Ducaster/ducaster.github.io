데이터 모델과 SQL 마지막, 본질식별자와 인조식별자. 인조식별자를 쓸 때 생기는 문제(중복 데이터, 불필요한 인덱스)가 자주 나온다.

## 요약

- 본질식별자는 업무에 의해 자연스럽게 만들어지는 식별자이고, 인조식별자는 업무와 관계없이 인위적으로 만든 식별자다.
- 본질식별자가 여러 속성으로 복잡하게 이루어질 때 인조식별자를 쓴다.
- 인조식별자는 단순하고 편하지만, 중복 데이터가 들어갈 수 있고 인덱스가 추가로 필요해질 수 있다.
- 인조식별자를 쓰더라도 본질식별자 조합에는 UNIQUE 제약을 걸어 중복을 막는 것이 좋다.

## 1. 두 식별자의 차이

주문 상품 엔터티를 예로 들어 보자. 업무적으로 '한 주문 안에서 같은 상품은 한 줄'이라면 (주문번호, 상품코드)가 자연스러운 식별자다.

| 구분 | 본질식별자 | 인조식별자 |
|---|---|---|
| 정의 | 업무에 의해 만들어지는 식별자 | 업무적으로 만들어지지 않지만, 원래 식별자가 복잡해서 인위적으로 만든 식별자 |
| 예 | 주문상품(주문번호 + 상품코드) | 주문상품(주문상품번호: 1, 2, 3…) |
| 값의 의미 | 업무적 의미가 있다 | 의미 없는 일련번호다 |
| 생성 방법 | 업무 데이터 그대로 | 시퀀스(SEQUENCE), IDENTITY 컬럼, 최댓값 + 1 |

## 2. 인조식별자의 장단점

| 장점 | 단점 |
|---|---|
| 식별자가 단일 속성이라 단순하다 | 같은 주문번호 + 상품코드 조합이 여러 번 들어가는 중복 데이터가 생길 수 있다 |
| 자식 테이블로 물려줄 PK 속성이 적어 조인과 SQL이 간단해진다 | 실제 조회는 주문번호와 상품코드로 하므로, PK 인덱스 외에 인덱스가 하나 더 필요해진다 |
| 본질식별자 값이 바뀌어도 PK는 그대로다 | 값에 업무 의미가 없어 데이터만 보고 무엇인지 알기 어렵다 |

### 중복을 막는 방법

인조식별자를 PK로 쓰면, 데이터베이스는 주문상품번호만 다르면 같은 주문의 같은 상품이 두 번 들어와도 막지 못한다. 그래서 본질식별자 조합에 UNIQUE 제약을 걸어 둔다.

```sql
CREATE TABLE ORDER_ITEM (
  ITEM_ID   NUMBER        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 인조식별자
  ORDER_NO  NUMBER        NOT NULL,
  PROD_CODE VARCHAR2(10)  NOT NULL,
  QTY       NUMBER        NOT NULL,
  CONSTRAINT UQ_ORDER_ITEM UNIQUE (ORDER_NO, PROD_CODE)              -- 본질식별자 중복 방지
);
```

`GENERATED ALWAYS AS IDENTITY`는 Oracle 12c부터 쓸 수 있는 자동 증가 컬럼이다. 그 전에는 시퀀스(`CREATE SEQUENCE`)를 만들어 `시퀀스명.NEXTVAL`로 값을 넣었다. UNIQUE 제약은 내부적으로 인덱스를 만들기 때문에, 결과적으로 이 테이블에는 PK 인덱스와 UNIQUE 인덱스 두 개가 생긴다. 인조식별자의 '인덱스 추가' 단점이 바로 이것이다.

> **쉬운 설명**
>
> 학생을 '반 + 번호'로 부르면 본질식별자, 입학할 때 받은 학번으로 부르면 인조식별자다. 학번은 짧고 반이 바뀌어도 그대로라 편하지만, 학번만 보고는 몇 반 몇 번인지 알 수 없고, 실수로 같은 학생에게 학번을 두 개 주면 시스템이 막아 주지 못한다. 그래서 '반 + 번호' 조합은 겹치지 않게 따로 규칙을 걸어 둔다.

## 3. 무엇을 쓸까

- 본질식별자가 한두 개 속성으로 간단하고 잘 바뀌지 않으면 본질식별자를 그대로 쓴다.
- 본질식별자가 많은 속성으로 이루어져 자식 테이블까지 PK가 길게 이어지면 인조식별자를 검토한다.
- 인조식별자를 쓰기로 했다면 본질식별자에 UNIQUE 제약을 함께 건다.

## 헷갈렸던 것들

- 인조식별자의 단점은 **중복 데이터 발생 가능성**과 **불필요한 인덱스 생성**이다.
- 인조식별자는 업무적으로 만들어지지 않은, 의미 없는 식별자다.
- 인조식별자를 쓰면 실제 조회 조건인 본질식별자 컬럼에 별도의 인덱스가 필요해질 수 있다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 본질식별자 | 업무에 의해 만들어진 식별자 |
| 인조식별자 | 인위적으로 만든 일련번호 같은 식별자 |
| 시퀀스 | 일련번호를 자동으로 만들어 주는 Oracle 객체 |
| IDENTITY 컬럼 | 값이 자동으로 증가하는 컬럼 |
| UNIQUE 제약 | 컬럼 값의 중복을 막는 제약 |

## 복습 문제

**1.** 인조식별자에 대한 설명으로 옳지 않은 것은?

① 원래 식별자가 복잡할 때 인위적으로 만든다 ② 중복 데이터가 들어갈 가능성이 있다 ③ 업무적인 의미가 있어 값만 보고 대상을 알 수 있다 ④ 불필요한 인덱스가 생길 수 있다

**2.** 주문상품 테이블의 PK를 인조식별자 '주문상품번호'로 바꿨을 때, 같은 주문의 같은 상품이 두 번 입력되는 것을 막는 방법으로 알맞은 것은?

① 주문상품번호에 NOT NULL 제약을 건다 ② 주문번호와 상품코드 조합에 UNIQUE 제약을 건다 ③ 수량에 CHECK 제약을 건다 ④ 주문상품번호를 문자형으로 바꾼다

## 답과 풀이

1. ③ 인조식별자는 업무 의미가 없는 값이다.
2. ② 본질식별자 조합에 UNIQUE 제약을 걸어 중복을 막는다.
