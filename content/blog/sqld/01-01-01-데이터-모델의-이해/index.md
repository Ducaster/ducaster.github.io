SQLD 1과목 '데이터 모델링의 이해' 첫 번째, 데이터 모델의 이해. 모델링의 세 가지 특징과 관점, 개념·논리·물리 모델링의 차이, 3층 스키마와 데이터 독립성이 자주 나온다.

## 요약

- 모델링은 복잡한 현실 세계를 단순하게 표현하는 일이고, 추상화, 단순화, 명확화가 특징이다.
- 모델링은 데이터(What), 프로세스(How), 데이터와 프로세스의 상관(Interaction) 관점으로 본다.
- 데이터 모델링은 개념적 → 논리적 → 물리적 순서로 구체화된다.
- 3층 스키마(외부, 개념, 내부)는 데이터 독립성을 보장하려고 데이터베이스 구조를 세 단계로 나눈다.
- 데이터 모델은 엔터티(Things), 속성(Attributes), 관계(Relationships)의 세 요소로 이루어진다.

## 1. 모델링

### 모델링의 특징

**모델링(modeling)** 은 현실 세계를 일정한 표기법으로 단순하게 표현하는 일이다.

| 특징 | 뜻 |
|---|---|
| 추상화(Abstraction) | 현실 세계를 일정한 형식에 맞춰 표현한다. 공통점만 뽑아 개념으로 만든다 |
| 단순화(Simplification) | 복잡한 현실을 약속된 규약과 제한된 표기법으로 쉽게 표현한다 |
| 명확화(Clarity) | 누구나 이해하기 쉽게, 애매함 없이 정확하게 표현한다 |

### 모델링의 세 관점

| 관점 | 질문 | 내용 |
|---|---|---|
| 데이터 관점 | What | 업무가 어떤 데이터와 관련 있는지, 데이터끼리 어떤 관계인지 |
| 프로세스 관점 | How | 업무가 실제로 무엇을 하는지, 무엇을 해야 하는지 |
| 데이터와 프로세스의 상관 관점 | Interaction | 업무 처리 방법에 따라 데이터가 어떤 영향을 받는지(CRUD: 생성, 조회, 수정, 삭제) |

### 데이터 모델링의 중요성과 유의점

데이터 모델은 시스템의 뼈대라서 한번 잘못 만들면 고치기가 매우 어렵다.

| 중요성 | 설명 |
|---|---|
| 파급효과(Leverage) | 시스템 구축 막바지에 데이터 모델을 바꾸면 수많은 프로그램과 테이블을 함께 고쳐야 한다 |
| 복잡한 요구사항의 간결한 표현(Conciseness) | 데이터 모델은 요구사항을 가장 간결하게 보여 주는 도구다 |
| 데이터 품질(Data Quality) | 잘못 설계된 모델은 중복과 불일치를 만들어 데이터 품질을 떨어뜨린다 |

| 유의점 | 설명 |
|---|---|
| 중복(Duplication) | 같은 정보를 여러 곳에 저장하지 않게 한다 |
| 비유연성(Inflexibility) | 사소한 업무 변화에도 모델을 크게 바꿔야 하는 일이 없도록, 데이터 정의와 프로세스를 분리한다 |
| 비일관성(Inconsistency) | 데이터끼리의 상호 연관 관계를 명확히 정의해 서로 모순되지 않게 한다 |

## 2. 데이터 모델링의 3단계

{{< mermaid >}}
flowchart LR
  C["개념적 모델링<br>업무 중심, 전사적"] --> L["논리적 모델링<br>키, 속성, 관계, 정규화"]
  L --> P["물리적 모델링<br>테이블, 인덱스, 성능"]
{{< /mermaid >}}

| 단계 | 내용 | 추상화 수준 |
|---|---|---|
| 개념적 데이터 모델링 | 업무 중심의 핵심 엔터티와 관계를 포괄적으로 정의한다. 전사적 데이터 모델링, EA(Enterprise Architecture) 수립 때 많이 한다 | 높음 |
| 논리적 데이터 모델링 | 시스템으로 구축할 업무의 키, 속성, 관계를 정확하게 표현한다. 정규화를 수행하며 재사용성이 높다 | 중간 |
| 물리적 데이터 모델링 | 실제 데이터베이스에 만들 테이블, 컬럼 타입, 인덱스를 정하고 성능과 저장 공간 같은 물리적 성격을 고려한다 | 낮음 |

> **쉬운 설명**
>
> 집을 짓는 과정과 같다. '방 셋, 거실 하나, 부엌 하나'를 정하는 게 개념적 모델링, 방 크기와 문 위치, 방끼리 어떻게 이어지는지 도면으로 그리는 게 논리적 모델링, 벽돌 종류와 배관 굵기까지 정해 실제로 짓는 게 물리적 모델링이다.

## 3. 3층 스키마와 데이터 독립성

**스키마(schema)** 는 데이터베이스의 구조와 제약 조건을 정의한 것이다. ANSI/SPARC는 사용자와 저장 장치 사이를 세 단계로 나눈 **3층 스키마(3-Level Schema)** 를 제시했다. 목적은 **데이터 독립성**이다. 한 단계를 바꿔도 다른 단계에 영향을 주지 않게 하는 거다.

{{< mermaid >}}
flowchart TB
  U1["사용자 A"] --- E1["외부 스키마 A<br>(뷰)"]
  U2["사용자 B"] --- E2["외부 스키마 B<br>(뷰)"]
  E1 ---|"논리적 사상"| C["개념 스키마<br>전체 통합 구조"]
  E2 ---|"논리적 사상"| C
  C ---|"물리적 사상"| I["내부 스키마<br>물리적 저장 구조"]
  I --- DB[("데이터베이스")]
{{< /mermaid >}}

| 스키마 | 관점 | 내용 |
|---|---|---|
| 외부 스키마(External) | 사용자 관점 | 각 사용자나 응용 프로그램이 보는 데이터베이스의 일부. 여러 개가 있을 수 있다(서브 스키마, 뷰) |
| 개념 스키마(Conceptual) | 통합 관점 | 모든 사용자의 관점을 통합한 전체 데이터베이스의 논리적 구조. 하나만 있다 |
| 내부 스키마(Internal) | 물리적 저장 관점 | 데이터가 실제로 저장되는 방식(파일 구조, 인덱스, 레코드 형식) |

| 독립성 | 뜻 |
|---|---|
| 논리적 독립성 | 개념 스키마가 바뀌어도 외부 스키마(응용 프로그램)에는 영향이 없다 |
| 물리적 독립성 | 내부 스키마(저장 구조)가 바뀌어도 개념 스키마에는 영향이 없다 |

외부 스키마와 개념 스키마를 잇는 것을 **논리적 사상(외부적/개념적 사상)**, 개념 스키마와 내부 스키마를 잇는 것을 **물리적 사상(개념적/내부적 사상)** 이라고 한다.

> **쉬운 설명**
>
> 도서관에 비유하면, 이용자가 검색창에서 보는 화면이 외부 스키마, 사서가 관리하는 전체 장서 목록이 개념 스키마, 책이 실제로 꽂힌 서가 배치가 내부 스키마다. 서가 배치를 바꿔도(내부) 장서 목록은 그대로고(물리적 독립성), 장서 목록에 항목을 추가해도 이용자 검색 화면은 그대로 쓸 수 있다(논리적 독립성).

## 4. 데이터 모델의 구성 요소

데이터 모델은 세 가지 요소로 이루어진다.

| 요소 | 뜻 | 예 |
|---|---|---|
| 엔터티(Entity) | 업무가 관여하는 어떤 것(Things) | 사원, 부서 |
| 속성(Attribute) | 어떤 것이 가지는 성격 | 사원명, 입사일 |
| 관계(Relationship) | 어떤 것끼리의 관계 | 사원은 부서에 소속된다 |

| 개념 | 집합(타입) | 개별 값(인스턴스) |
|---|---|---|
| 어떤 것 | 엔터티 타입(엔터티) | 엔터티 인스턴스(어커런스) |
| 어떤 것끼리의 연관 | 관계 | 페어링(pairing) |
| 어떤 것의 성격 | 속성 | 속성값 |

예를 들어 '사원'이 엔터티라면 '1005 정대리'는 인스턴스, '사원명'은 속성, '정대리'는 속성값이다.

## 5. ERD

**ERD(Entity Relationship Diagram)** 는 엔터티와 관계를 그림으로 표현한 것으로, 1976년 피터 첸(Peter Chen)이 처음 제안했다. 표기법으로는 첸(Chen) 표기법, 실무에서 많이 쓰는 **IE(Information Engineering) 표기법**(까마귀발 표기법), **바커(Barker) 표기법**이 있다.

ERD는 보통 다음 순서로 그린다.

1. 엔터티를 그린다.
2. 엔터티를 적절하게 배치한다(중요한 엔터티는 왼쪽 위에).
3. 엔터티 사이에 관계를 설정한다.
4. 관계명을 적는다.
5. 관계의 참여도(1:1, 1:N 등)를 적는다.
6. 관계의 필수 여부(필수, 선택)를 적는다.

### 좋은 데이터 모델의 요소

| 요소 | 뜻 |
|---|---|
| 완전성(Completeness) | 업무에 필요한 데이터가 모두 정의되어 있다 |
| 중복 배제(Non-Redundancy) | 같은 사실은 한 번만 기록한다 |
| 업무 규칙(Business Rules) | 업무 규칙이 모델에 표현되어 있다 |
| 데이터 재사용(Data Reusability) | 데이터를 통합하고 독립적으로 설계해 재사용성을 높인다 |
| 의사소통(Communication) | 모델을 보고 업무 규칙을 이해할 수 있다 |
| 통합성(Integration) | 같은 데이터는 조직 전체에서 한 번만 정의하고 공유한다 |

## 헷갈렸던 것들

- 모델링의 특징은 추상화, 단순화, 명확화다. '복잡화', '구체화'는 틀린 보기다.
- 정규화는 **논리적** 데이터 모델링 단계에서 한다.
- 추상화 수준은 개념적 > 논리적 > 물리적 순서로 높다.
- 논리적 독립성은 개념 스키마 변경이 외부 스키마에, 물리적 독립성은 내부 스키마 변경이 개념 스키마에 영향을 주지 않는 것이다.
- 개념 스키마는 하나, 외부 스키마는 여러 개일 수 있다.
- 데이터 모델링의 유의점은 중복, 비유연성, 비일관성이다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 모델링 | 현실 세계를 단순화해 표현하는 일 |
| 개념적 / 논리적 / 물리적 모델링 | 업무 중심 / 키·속성·관계와 정규화 / 실제 DB 구현 |
| 3층 스키마 | 외부, 개념, 내부 스키마 |
| 데이터 독립성 | 한 스키마의 변경이 다른 스키마에 영향을 주지 않는 성질 |
| 인스턴스 | 엔터티에 속하는 개별 대상 |
| ERD | 엔터티와 관계를 표현한 다이어그램 |

## 복습 문제

**1.** 데이터 모델링의 특징이 아닌 것은?

① 추상화 ② 단순화 ③ 구체화 ④ 명확화

**2.** 시스템으로 구축하려는 업무의 키, 속성, 관계를 정확하게 표현하고 정규화를 수행하는 단계는?

① 개념적 데이터 모델링 ② 물리적 데이터 모델링 ③ 프로세스 모델링 ④ 논리적 데이터 모델링

**3.** 모든 사용자의 관점을 통합한 데이터베이스 전체의 논리적 구조를 나타내는 스키마는?

① 외부 스키마 ② 내부 스키마 ③ 서브 스키마 ④ 개념 스키마

**4.** 저장 구조를 바꿔도 개념 스키마에 영향을 주지 않는 성질은?

① 논리적 독립성 ② 무결성 ③ 일관성 ④ 물리적 독립성

**5.** 데이터 모델링 시 유의점이 아닌 것은?

① 중복 ② 정규화 ③ 비유연성 ④ 비일관성

## 답과 풀이

1. ③ 모델링의 특징은 추상화, 단순화, 명확화다.
2. ④ 논리적 데이터 모델링에서 정규화를 수행한다.
3. ④ 개념 스키마는 전체를 통합한 구조이고 하나만 있다.
4. ④ 내부 스키마의 변경이 개념 스키마에 영향을 주지 않는 것은 물리적 독립성이다.
5. ② 정규화는 유의점이 아니라 좋은 모델을 만드는 방법이다.
