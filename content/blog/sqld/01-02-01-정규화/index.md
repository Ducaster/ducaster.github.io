1과목 '데이터 모델과 SQL' 파트 첫 번째, 정규화. 테이블을 주고 몇 정규형인지, 어떤 종속을 없애야 하는지 묻는 문제가 많아서 같은 테이블을 단계별로 쪼개 가며 정리했다.

## 요약

- 정규화는 데이터 중복을 줄이고 이상현상(삽입, 갱신, 삭제 이상)을 없애려고 테이블을 나누는 과정이다.
- 정규화는 함수 종속성을 근거로 한다. X의 값이 Y의 값을 하나로 정하면 'X → Y'라고 쓴다.
- 제1정규형은 원자값, 제2정규형은 부분 함수 종속 제거, 제3정규형은 이행 함수 종속 제거, BCNF는 모든 결정자가 후보키가 되게 하는 것이다.
- 정규화하면 입력, 수정, 삭제 성능이 좋아지지만, 조회할 때 조인이 늘어날 수 있다.

## 1. 이상현상

중복이 많은 테이블은 데이터를 바꿀 때 문제가 생긴다. 다음은 정규화하지 않은 주문 테이블이다.

| 주문번호 | 주문일자 | 고객번호 | 고객명 | 상품코드 | 상품명 | 수량 |
|---|---|---|---|---|---|---|
| 1 | 2024-10-01 | C1 | 홍길동 | P1 | 연필 | 3 |
| 1 | 2024-10-01 | C1 | 홍길동 | P2 | 지우개 | 1 |
| 2 | 2024-10-02 | C2 | 김영희 | P1 | 연필 | 5 |

| 이상현상 | 설명 | 위 테이블의 예 |
|---|---|---|
| 삽입 이상(Insertion Anomaly) | 원하지 않는 정보까지 함께 넣어야 데이터를 넣을 수 있다 | 새 상품 '공책'은 주문이 들어오기 전까지 등록할 수 없다 |
| 갱신 이상(Update Anomaly) | 중복된 데이터 일부만 바뀌어 서로 맞지 않게 된다 | '연필'을 '색연필'로 바꿀 때 한 행만 고치면 상품명이 둘이 된다 |
| 삭제 이상(Deletion Anomaly) | 데이터를 지우면 지우면 안 되는 정보까지 함께 사라진다 | 주문 2를 지우면 고객 김영희의 정보도 사라진다 |

## 2. 함수 종속성

**함수 종속(Functional Dependency)** 은 어떤 속성 X의 값을 알면 다른 속성 Y의 값이 하나로 정해지는 관계다. 'X → Y'로 쓰고, X를 **결정자**, Y를 **종속자**라고 한다.

- 상품코드 → 상품명 (상품코드를 알면 상품명이 정해진다)
- 고객번호 → 고객명
- (주문번호, 상품코드) → 수량

## 3. 정규형

| 정규형 | 조건 | 해결 방법 |
|---|---|---|
| 제1정규형(1NF) | 모든 속성이 원자값(하나의 값)만 가진다. 반복되는 속성 그룹이 없다 | 다중값 속성을 별도 행이나 테이블로 분리 |
| 제2정규형(2NF) | 1NF이면서, 기본키가 여러 속성으로 되어 있을 때 일반 속성이 기본키 전체에 종속된다(부분 함수 종속이 없다) | 기본키 일부에만 종속된 속성을 분리 |
| 제3정규형(3NF) | 2NF이면서, 일반 속성끼리 종속되지 않는다(이행 함수 종속이 없다) | A → B → C에서 B → C 부분을 분리 |
| BCNF(Boyce-Codd) | 3NF이면서, 모든 결정자가 후보키다 | 후보키가 아닌 결정자를 분리 |
| 제4정규형(4NF) | 다치 종속(다중값 종속)이 없다 | |
| 제5정규형(5NF) | 조인 종속이 없다 | |

### 예제로 보는 정규화

위의 주문 테이블은 한 행에 값이 하나씩이라 이미 1NF이다(한 칸에 '연필, 지우개'처럼 여러 값이 들어 있었다면 1NF가 아니다). 기본키는 (주문번호, 상품코드)이다.

**2NF:** 상품명은 기본키의 일부인 상품코드에만 종속되고, 주문일자, 고객번호, 고객명은 주문번호에만 종속된다. 이런 부분 함수 종속을 분리한다.

- 주문(**주문번호**, 주문일자, 고객번호, 고객명)
- 주문상품(**주문번호, 상품코드**, 수량)
- 상품(**상품코드**, 상품명)

**3NF:** 주문 테이블에서 주문번호 → 고객번호 → 고객명이라는 이행 함수 종속이 남아 있다. 고객 정보를 분리한다.

- 주문(**주문번호**, 주문일자, 고객번호)
- 고객(**고객번호**, 고객명)

이제 새 상품은 주문 없이 상품 테이블에 넣을 수 있고, 상품명은 한 곳만 고치면 되며, 주문을 지워도 고객 정보는 남는다.

**BCNF 예:** 수강(**학생, 과목**, 교수) 테이블에서 교수 한 명이 한 과목만 가르친다면 '교수 → 과목'이 성립한다. 교수는 결정자지만 후보키가 아니므로 BCNF가 아니다. 수강(**학생, 교수**)과 담당(**교수**, 과목)으로 나눈다.

> **쉬운 설명**
>
> 반 연락망에 담임 선생님 전화번호를 학생마다 적어 두면, 선생님 번호가 바뀔 때 30줄을 다 고쳐야 하고 한 줄이라도 놓치면 번호가 둘이 된다(갱신 이상). 정규화는 '선생님 번호는 선생님 표에 한 번만 적고, 학생 표에는 담임이 누구인지만 적자'는 정리 방법이다.

## 4. 정규화와 성능

| 작업 | 정규화의 영향 |
|---|---|
| 입력, 수정, 삭제 | 중복이 줄어 한 곳만 바꾸면 되므로 대체로 좋아진다 |
| 조회 | 여러 테이블을 조인해야 해서 느려질 수 있다. 다만 테이블이 작아지고 중복이 줄어 오히려 빨라지는 경우도 있다 |

조회 성능이 꼭 필요하면 일부러 중복을 허용하는 **반정규화(denormalization)** 를 검토한다. 반정규화는 데이터 무결성을 해칠 수 있어서, 성능 문제가 분명할 때 신중하게 적용한다.

## 헷갈렸던 것들

- 1NF는 원자값, 2NF는 **부분** 함수 종속 제거, 3NF는 **이행** 함수 종속 제거다. 순서를 바꾼 보기가 자주 나온다.
- 기본키가 하나의 속성이면 부분 함수 종속이 생길 수 없어 1NF이면 곧 2NF이다.
- BCNF는 모든 결정자가 후보키여야 한다.
- 정규화는 논리적 데이터 모델링 단계에서 한다.
- 정규화를 하면 '조회 성능이 항상 나빠진다'는 말은 틀렸다.
- 이상현상은 삽입, 갱신(수정), 삭제 이상 세 가지다. '조회 이상'은 없다.

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 정규화 | 중복과 이상현상을 없애려고 테이블을 나누는 과정 |
| 이상현상 | 삽입, 갱신, 삭제 때 생기는 문제 |
| 함수 종속 | X 값이 Y 값을 하나로 정하는 관계(X → Y) |
| 부분 함수 종속 | 복합 기본키의 일부에만 종속되는 것 |
| 이행 함수 종속 | A → B, B → C일 때 A → C가 성립하는 것 |
| BCNF | 모든 결정자가 후보키인 정규형 |
| 반정규화 | 성능을 위해 일부러 중복을 허용하는 것 |

## 복습 문제

**1.** 기본키 (학번, 과목코드)인 테이블에서 '과목명'이 과목코드에만 종속될 때 위반하는 정규형은?

① 제1정규형 ② 제3정규형 ③ 제2정규형 ④ BCNF

**2.** 사원(**사원번호**, 사원명, 부서번호, 부서명) 테이블에서 부서명을 분리해야 하는 이유는?

① 이행 함수 종속이 있어서 ② 원자값이 아니어서 ③ 부분 함수 종속이 있어서 ④ 다치 종속이 있어서

**3.** 이상현상에 해당하지 않는 것은?

① 삽입 이상 ② 갱신 이상 ③ 삭제 이상 ④ 조회 이상

**4.** 정규화에 대한 설명으로 옳지 않은 것은?

① 데이터 중복을 줄인다 ② 이상현상을 없앤다 ③ 논리적 데이터 모델링 단계에서 수행한다 ④ 정규화를 하면 조회 성능은 항상 나빠진다

## 답과 풀이

1. ③ 복합 기본키의 일부에만 종속되는 부분 함수 종속이 있으므로 2NF를 위반한다.
2. ① 사원번호 → 부서번호 → 부서명의 이행 함수 종속이 있어 3NF를 위반한다.
3. ④ 이상현상은 삽입, 갱신, 삭제 세 가지다.
4. ④ 조인이 늘어 느려질 수도 있지만, 항상 그런 것은 아니다.
